# Architecture

## Overview

Career Atlas is a local website. One Node process serves the React app and the JSON API on `127.0.0.1`; all data lives in a local SQLite database.

```
Browser (React SPA, EN/中文)  http://127.0.0.1:4310
   │  same-origin fetch /api/*  (JSON)
   ▼
src/local/runtime.ts   firewall: Host must be loopback (DNS rebinding), same-origin writes only
   │                   static SPA (dist/client) with strict CSP
   ▼
src/server/app.ts      Hono: request id → CSRF/content-type → local user → routes → services
   │
   ├─ env.DB      LocalD1: D1-style API over node:sqlite (WAL, FULL sync, FKs on, atomic batch)
   ├─ env.FILES   local document store (~/Library/Application Support/CareerAtlas/documents)
   ├─ env.EXTRACTION_DISPATCH ──► in-process task runner ──► extraction pipeline
   │                               (retries, resumes after restart)   (ATS API → JSON-LD → HTML → rules → optional AI)
   └─ env.AI_LOCAL  optional Claude Code CLI, only for extractions you start with AI
Weekly encrypted backups (src/local/backup.ts) → ~/CareerAtlasBackups
```

Operations (start, data locations, autosave, backups, restore, AI): [docs/LOCAL_FIRST.md](docs/LOCAL_FIRST.md).

## Key decisions

| Decision | Choice | Why |
|---|---|---|
| Runtime | Node ≥ 22.16, `@hono/node-server`, one process, 127.0.0.1 | Simple, no services or containers; runs only while you use it |
| API | Hono + zod | Small, typed validation, runtime-independent |
| DB | SQLite (`node:sqlite`, no native build) + Drizzle; D1-style adapter | The app began on Cloudflare D1; keeping that small API let every service move unchanged |
| Durability | WAL + `synchronous=FULL`, FKs on, atomic batches, verified backups before migrations | A personal journal must not lose data |
| Background work | In-process runner; the extraction row is the durable queue entry | Save first, extract second; resumes after restart; nothing runs when the app is closed |
| Auth | Single local user + loopback/Host/Origin firewall | No accounts needed locally; `user_id` scoping kept for future multi-user |
| AI | Optional Claude Code CLI, subscription auth only, on request only | No API billing, no extra infrastructure; rule-based extraction always works |
| Frontend | React 19, React Router 7, TanStack Query/Table, Radix primitives, Tailwind v4, dnd-kit, Recharts | Mature, accessible, maintainable |
| i18n | i18next, typed catalogs, `Intl` in the user's time zone | Bilingual by construction |
| Versions | Pinned exact versions ≥ 2 weeks old | Reproducible builds; avoid fresh majors |

## Data model in one paragraph

A **job posting** (facts from the employer) belongs to a **company**. A **saved job** is your relationship to a posting: stage `saved/preparing/closed`, priority, tags, notes and materials. An **application** exists only after you actually apply. It holds the lifecycle status `applied → … → offer/accepted/rejected/withdrawn/closed` plus monotonic milestone timestamps. `application_events` is an append-only log. Extraction runs live in `job_extraction_jobs`. What the source looked like is kept in `job_source_snapshots`. Field provenance is in `extracted_field_evidence`, and manual edits in `user_field_overrides`. See [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md).

## Status machine

`services/pipeline.ts › changeStatus` is the only place status changes happen. It writes the state change and its event in one atomic batch (one SQLite transaction):

- **Pre-application → application status:** creates the application and an `application_submitted` event, plus an automatic follow-up reminder (default 7 days; this is only a nudge).
- **An application never moves back to `saved`/`preparing`.** That returns a 409; use Withdrawn or Closed instead.
- **Milestones** (`reached_interview_at`, …) are set the first time a stage is reached and never cleared. Analytics therefore count historical conversion correctly.
- **Editing or deleting events** recomputes milestones from the log.
- **Time never marks an application as Rejected.** Waiting time only drives reminders.

## Extraction pipeline

`extraction/pipeline.ts › runPipeline` is pure (network injected) and tested without a database.

1. **Detect the platform** from the URL (`platforms.ts`). LinkedIn, Indeed, Glassdoor and similar sites are *not fetched*. They return `access_restricted / platform_restricted` and the link stays saved.
2. **Public ATS API adapters.**
   - Greenhouse boards API (`pay_transparency`), Lever postings API, Ashby posting API (`includeCompensation`), SmartRecruiters postings API, Workday CXS JSON.
   - A 404 from these APIs suggests the posting is closed.
3. **Otherwise fetch the page with `safeFetch`.**
   - Guardrails: http(s) only; default ports only; private, loopback, link-local and metadata destinations blocked (literal IPs and every DNS answer, IPv4 and IPv6).
   - Redirects are followed manually and re-validated, at most 5.
   - Limits: 12 s timeout, 3 MB, allowed content types only.
   - The resolved address is checked again when the connection opens (no DNS rebinding).
4. **Parse the page.** JSON-LD `JobPosting`, then meta tags, then main-region text.
   - Detects bot walls, login walls and JS-only shells. These get honest `access_restricted` or `dynamic_content` results rather than a guess.
5. **Rule-based extraction** (`heuristics.ts`) runs on the text, always and without AI.
   - Covers sections, work mode and office frequency, employment type, salary (currency and period only when stated), experience, education, languages, work authorization vs. sponsorship (kept separate), citizenship, clearance, remote-eligible regions and deadline.
   - Each value carries the exact sentence it came from.
6. **AI (optional, only when the user ticks "Use Claude AI")** via the `AiProvider` adapter (local Claude Code CLI with no tools).
   - System instructions and untrusted posting content are isolated in separate messages. The content sits inside delimiters, with any delimiter injection stripped.
   - Output is zod-validated.
   - Evidence must be a verbatim quote from the posting. If not, sensitive fields (salary, visa, authorization, location eligibility, work mode, deadline) are dropped, and other fields are downgraded to low confidence. Salary numbers must also appear in the quote.
7. **Merge.** Candidates are ranked by confidence, then source (ATS API > JSON-LD > AI > rules > metadata).
   - Disagreements become `conflict` with alternatives.
   - Low confidence, conflicts, sensitive values from AI or rules, and incomplete salaries are marked `needs_review`.
8. **Outcome.** One of `succeeded`, `partial` (core fields missing), `needs_review`, `access_restricted` or `failed`.
   - Stale runs (more than 5 minutes) become `failed / timeout`, so the UI never spins forever.
   - Transient errors (timeouts, 5xx, 429) are retried by the task runner with backoff, up to 3 attempts. Runs interrupted by a quit or crash resume at the next start.

Nothing extracted is written to the posting until the user **applies** the review. The original JD text, however, is preserved immediately as a snapshot. A refresh creates a new snapshot. The UI shows only changed fields and pre-selects them, *except* fields the user edited manually.

## Frontend

- **Shell:** desktop sidebar plus top bar (global search ⌘K, Add job `N`); mobile drawer, bottom bar and floating add button.
- **URL-synced state:** filters, tabs and views live in the URL, so a language switch or reload keeps them.
- **Data fetching:** TanStack Query with targeted invalidation. The board uses optimistic updates with rollback.
- **Saving:** every write is a mutation; the header shows Saving / Saved / Failed. Free-text fields autosave after a short pause (`useAutosaveText`); closing the tab with pending or unsent text asks first.
- **Dates:** every date is rendered with `Intl` in the user's time zone (default `America/Toronto`). Date inputs convert local time to UTC epoch ms.
- **Visual system:** warm-neutral tokens in `index.css`, a single accent color, and status colors used sparingly.

## Future extensions

The architecture leaves room for these without building them now:

- **Gmail:** a separate OAuth integration with minimal scopes (Gmail read scopes are Restricted and need Google verification and a possible security assessment).
  - It would add tables such as `integrations` and `email_messages` (metadata only), plus a matcher that *proposes* events.
  - Proposed status changes would go through the same `changeStatus` service, but only after user confirmation.
- **Browser extension:** would call `POST /api/jobs/capture` using a scoped API token (a new `AuthProvider`), with minimal host permissions.
- **Google Calendar:** a one-way export first. The built-in calendar and `.ics` export already work on their own.
- **AI assistant:** answers would come from SQL over the existing read models (`listJobs`, `getAnalytics`), never from guesses. No vector database is needed.
